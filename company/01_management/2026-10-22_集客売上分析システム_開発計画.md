# 集客・売上分析システム｜開発計画（2026-10-22）

> **この文書は計画のみです。** コードは書いていません。
> 既存ファイルの変更・外部サービスへの接続・認証情報の取得・データの送信や削除・配信は、一切していません。
> 実装は、末尾の【要確認】への回答と、明示的な承認をいただいてから始めます。

---

## 全体像：数字の仕組みは「1本」です（別のシステムを増やさない）

本日すでに動き出した**数字の記録（第1段階）**と、この計画書の**分析システム（第2段階）**は、
別々のものではなく**同じ1本の仕組みの段階違い**です。混ぜても、ややこしくならないように設計します。

| 段階 | 中身 | 状態 | 代表の作業 |
|---|---|---|---|
| **第1段階｜記録する** | 毎週金曜、チャットで数字を5つまで聞く → `_shared/metrics.csv` に1行 | **✅ `main` に反映済み。10/23（金）から開始** | 週2分（チャット） |
| **第2段階｜分析する** | 第1段階の数字に、配信ごと・投稿ごと・イベントごとの細かい数字（スクショ・月1回のCSV）を足す → 集計 → スプレッドシート → 週次分析レポート → 施策ログ | **本計画書。承認待ち** | 週5分＋月15分 |
| 第3段階｜（必要なら）個票を使う | 「どこから来た人が申し込んだか」を見る。Google内で完結する方式（下の案C） | 将来・未定 | — |

**3つの約束（混乱しないためのルール）**

1. **入口はずっと1つ**：金曜の `/weekly` でチャットに答えるだけ。第2段階に進んでも、**「スクショを貼る」が増えるだけ**です
2. **数字の置き場もずっと1つ**：第2段階では `metrics.csv` と記録用の道具を新しいフォルダ `company/analytics/` に**引っ越し**、そこに細かいデータを足していきます。**同じ数字を2か所に持ちません**
3. **リズムもずっと1つ**：週の区切りは、**すでに始まった金曜基準に合わせます**（下の【要確認】2の推奨を変更しました）

**判断のタイミング**：第1段階を**4週回したあと（11/20ごろ）**、記録が続いているかを見て、第2段階に進むかを決めます。
続いていれば、そのまま第2段階へ。止まっていれば、第2段階の前に**聞く数字を減らします**。
（※ 試作＝架空データでの開発は、それより先に進めても運用に影響しません）

## 0. 結論（先に）

1. **データは「集計系」と「個票系」の2種類に分けて扱います。**
   - **集計系**（開封数・クリック数・友だち数・リーチ数・イベントごとの申込数など）：個人情報が入っていません。**この系統だけで、ご要望の5機能はすべて実現できます**
   - **個票系**（読者リスト・申込者一覧・決済明細）：名前やメールが入っています。**初期開発では使いません**（架空データで試作）
2. **計算はリポジトリ内のスクリプトで行い、Googleスプレッドシートは「見る場所」にします。**
   初期は、**接続も認証情報も使わない方法**でスプレッドシートに載せます。
3. **入力は「月1回のCSV」と「週1回の画面スクショ」の組み合わせを推奨します。**
   この会社の実績では、**チャットで済む作業は100%進み、別のアプリを開く作業は進んでいません**（`HOW_TO_RUN.md`）。
   毎週3つのサービスからCSVを書き出す運用は、続かない可能性が高いと判断しています。

## 3. データ項目と計算式

### 3-1. 共通ルール

| 項目 | 定義 |
|---|---|
| 週 | **土曜〜金曜（日本時間）**。表記は金曜の日付。第1段階（`metrics.csv`・金曜の `/weekly`）と同じ基準【要確認2】 |
| 金額 | 税込・円。**受注額**（申込日基準）と**入金額**（入金日基準）を分けて持つ |
| 少数の扱い | 分母が30未満の率には「**参考値（n=○）**」と必ず表示。**率だけを単独で見せない** |
| 欠損 | 入力が無い週は**空欄のまま**。0で埋めない（「0件だった」と「記録が無い」を区別する） |
| 出典 | すべての数字に「どのファイル／どの画面、いつ取得」を記録する |

### 3-2. 計算式

**リスト**

| 指標 | 計算式 |
|---|---|
| 純増数 | 新規登録数 − 解除（ブロック）数 |
| 純増率 | 純増数 ÷ 週初の登録者数 |
| 解除率 | 解除数 ÷ 週初の登録者数 |
| 合計リスト数 | メルマガ読者数 ＋ LINE友だち数（**重複は除けない**ことを注記） |

**配信（メルマガ・LINE別々に）**

| 指標 | 計算式 | 備考 |
|---|---|---|
| 到達数 | 配信数 − 不達数 | 不達が取れない場合は配信数 |
| 開封率 | ユニーク開封数 ÷ 到達数 | 参考指標（上振れの可能性） |
| クリック率（CTR） | ユニーククリック数 ÷ 到達数 | **主指標** |
| クリック開封率（CTOR） | ユニーククリック数 ÷ ユニーク開封数 | 文面・導線の良し悪し |
| 配信あたり解除数 | 配信後48時間の解除数 | 取得可能なら |

**申込（リザストのイベント単位）**

| 指標 | 計算式 |
|---|---|
| 説明会申込率 | 説明会の申込数 ÷ その案内の到達数（メルマガ＋LINE） |
| 参加率 | 参加数 ÷ 申込数 |
| **成約率** | 本講座の申込数 ÷ 説明会の参加数 |
| リスト成約率 | 本講座の申込数 ÷ 募集開始時の合計リスト数 |
| 入金率 | 入金済み件数 ÷ 本講座の申込数 |
| プレミアム比率 | プレミアム申込数 ÷ 本講座の申込数 |

**売上**

| 指標 | 計算式 |
|---|---|
| 受注額 | Σ 申込金額（申込日の週に計上） |
| 入金額 | Σ 入金額 − Σ 返金額（入金日の週に計上） |
| 期の売上 | 9期など、イベント単位の入金額の合計 |
| 目標達成率 | 期の売上 ÷ 目標（最低74万円／満席148万円） |
| 1時間あたり売上 | 入金額 ÷（講座＋発信＋事務の時間） |

**施策の効果**

| 指標 | 計算式 |
|---|---|
| 変化量 | 施策期間の指標値 − 施策前の同じ長さの期間の値（ベースライン） |
| 判定 | 「改善／変化なし／悪化／**判定不能（n不足）**」の4つ。**n不足のときは判定しない** |

## 4. 週次分析レポートの形式（事実と推測の分離）

保存先：`company/analytics/reports/YYYY-MM-DD_週次分析.md`（スプレッドシートにも要約を載せる）

```
## 1. 事実（数字と出典のみ。AIの解釈を書かない）
   - 表：今週／先週／4週平均／差
   - 各数字に出典（例：LINE分析画面 10/26取得）
## 2. 推測（AIの解釈。必ず確度を付ける）
   - 「〇〇が原因の可能性（確度：低／中／高）。根拠：…」
   - 根拠が事実欄のどの数字かを明記
## 3. 未確認・データ不足
   - 足りないデータ、n不足で判定できないもの
## 4. 進行中の施策の状況（施策ログから自動）
## 5. 来週の施策候補（最大3つ・案A/B＋推奨）
```

**レポートの約束**
- 事実欄では「〜のため」「〜の影響で」と書かない（因果は推測欄だけ）
- 架空データで作ったレポートには、**冒頭と各ページに「架空データ」と大きく表示**する
- 施策候補に、**不安を煽る訴求・受講生や卒業生への依頼（感想・紹介・口コミ）を出さない**（`CLAUDE.md` の禁止事項）

## 5. 施策ログ（改善施策と結果の記録）

1施策＝1行。チャットで「この施策を始めた」と言えば、AIが行を作ります。

| 項目 | 例 |
|---|---|
| 施策ID | M-001 |
| 施策名 | 説明会の案内をLINEでも送る |
| 狙う段・指標 | 申込／説明会申込率 |
| 仮説 | メルマガを読まない層にLINEなら届く |
| 開始日・終了日 | 2026-11-02 〜 2026-11-15 |
| ベースライン | 施策前2週の値（自動） |
| 目標 | 申込 +3件 |
| 結果 | 終了日の翌週に自動計算 |
| 判定 | 改善／変化なし／悪化／判定不能 |
| 学び（代表の一言） | 任意 |

## 7. 開発手順とテスト方法

| フェーズ | 内容 | 成果物 | テスト | 代表の作業 |
|---|---|---|---|---|
| **0. 列名の確認** | 各ツールのCSVの**見出し行だけ**を確認 | 取込マッピング | — | 各CSVの見出し行（1行目）だけ、または画面のスクショを共有（**データ行は不要**） |
| **1. 定義** | データ定義書・計算式の確定 | docs/ | 代表が読んで○× | 10分 |
| **2. 架空データ** | リスト数百人規模・12週分・説明会→本講座の流れを再現 | sample/ | 生成結果が定義書どおりか自動確認 | なし |
| **3. 計算** | calc.js | src/ | **手計算した期待値と一致するか**のテスト。分母0・欠損週・返金・n不足 | なし |
| **4. 取込** | import.js | src/ | 列順の入れ替え・余分な列・Shift_JIS・重複行・日付書式違い。**個人情報列が出力に残らないこと**（メール・電話の形をした値を全出力から検索） | なし |
| **5. シート** | .xlsx生成 | 試作ファイル | 開いて見た目を確認 | **見て感想を言う（5分）** |
| **6. レポート** | 事実欄の自動生成＋推測欄の型 | 試作レポート | 「開封率急落」「申込0」「n不足」の3シナリオで、**事実と推測が混ざっていないか**を確認 | 読んで感想（5分） |
| **7. 施策ログ** | 記録と自動判定 | measures.csv | 架空の施策で前後比較が正しいか | なし |
| **8. 実データ切替** | **承認後のみ**。1回目は、管理画面の数字と突き合わせて検算 | 本番データ | 画面の数字との一致確認 | スクショ共有（10分） |

**フェーズ0〜7はすべて架空データで完結し、外部接続は不要です。**

## 8. 費用の見積もり方法

### 8-1. 初期費用

**式：初期費用 ＝ Σ（作業時間 × 時間単価） ＋ 新規ツール費**

| 内訳 | 見込み |
|---|---|
| 開発作業（フェーズ0〜7） | **AI側で約15〜20時間相当**（数回のセッションに分割） |
| 代表の作業 | **合計約30〜40分**（列名の共有・確認・感想） |
| 新規ツール費 | **0円の見込み**（既存の Google アカウント・リザスト・Claude の範囲内） |
| 外注する場合 | 上記時間 × 外注単価で換算（相場は依頼先により大きく異なるため、見積もり取得が必要） |

### 8-2. 継続運用コスト

**式：月額 ＝ 代表の作業時間 × 代表の時間単価 ＋ ツール費 ＋ 保守時間**

| 内訳 | 見込み |
|---|---|
| 週次：スクショ共有＋回答 | 約5分 × 4週 |
| 月次：集計系CSVの書き出し | 約15分 |
| 保守：ツール側のCSV形式が変わったとき | 1回1〜2時間（年に数回の想定） |
| ツール費 | 0円（案Bのコネクタ・案CのApps Scriptも無料枠内の見込み） |

> **代表の時間単価の目安**：直近の「1時間あたり入金額」（このシステムで出る数字）を使います。
> 運用コストがそれを超える指標は、**記録をやめる**判断をします。

## 9. 自動化できる部分／手動で残す部分

| 区分 | 内容 |
|---|---|
| **自動** | CSVの種類判定・個人情報列の除去・書式統一・重複排除／全指標の計算／4週平均との比較／n不足の警告／スプレッドシート用ファイルの生成／レポートの「事実」欄／施策の前後比較と判定 |
| **半自動（AIが下書き→代表が確認）** | レポートの「推測」欄／来週の施策候補／施策ログの行の作成 |
| **手動で残す** | 管理画面からのCSV書き出し・スクショ（APIの認証情報を持たないため）／noteの数字／作業時間・ワクワク度／**施策の最終判断**／**配信の送信（自動送信はしない）** |
| **やらない** | 個人単位の追跡（誰が何を開いたか）／リザスト・LINE・Stripeとの自動連携（認証情報が必要で、漏洩時の被害が大きい） |

## 10. セキュリティ上の注意点

1. **個票系CSVは、チャットにもリポジトリにも入れない。** 取込スクリプトは「許可した列だけ残す」方式（拒否リストではなく許可リスト）で、未知の列は捨てます
2. **gitは一度記録すると履歴から消えません。** 実データを入れる前に、リポジトリが**非公開（Private）**であることを確認してください（前回の提案書 7-2 で確認待ち）
3. スクショを共有するときは、**申込者名やメールアドレスが写っていない画面**だけにしてください（イベント一覧の件数だけの画面など）
4. 架空データは、ファイル名・列・レポート冒頭で**架空と明示**し、`kpi.md` などの本番の数字に**混ぜない**（`CLAUDE.md`：捏造禁止）
5. Googleとの連携（案B）を使う場合は、**特定の1ファイルだけに権限を絞る**。代表の判断で、いつでも連携を解除できます

## 11. この計画のリスク

| リスク | 対策 |
|---|---|
| **CSVの書き出しが続かない**（チャットの外の作業） | 週次はスクショ、CSVは月1回に限定。それでも止まったら、取得する指標を減らす |
| 数字が少なすぎて率がぶれる（説明会の参加数が数人など） | 率には必ず n を併記。判定は累計と4週平均で行う |
| 開封率を過信する | クリック率を主指標にする |
| 分析が目的化する | レポートの最後は必ず「来週の施策候補 最大3つ」で終える |
